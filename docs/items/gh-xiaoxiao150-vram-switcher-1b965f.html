English · Releases · IndexTTS 集成 · GPU 兼容性 · 和 llama-swap / berth 的区别 为本地 AI 情感陪伴（AstrBot / DeepSeek Harness）原生接入的 GPU 调度器 —— 让人设对话、IndexTTS 语音和自拍/改图在同一张 12 GB 卡上轮流用卡。 它不是通用 GPU 租约系统：不换客户端、不加代理、不读 nvidia-smi，只在宿主的事件边界上停/起你明确列出的进程。 在 12 GB 卡上，它把本地 LLM、IndexTTS 和 ComfyUI 从「互相换页」变成「轮流独占」——实测 s2mel 从 30 s/步回到 0.12 s/步，预填从 0.2 tok/s 回到 ~1300 tok/s。 它只负责这些「停/起」的顺序。不是模型、不是路由、也不是要你重写的启动器：所有机器相关的参数都在一个 JSON profile 里。 为什么需要它. 12 GB 卡上通常是这样： | 服务 | 常驻显存 | | llama-server（Qwen3.6-35B-A3B MoE，256K 上下文） | ~4.9 GB | | IndexTTS webui | ~2.3–5.3 GB | | ComfyUI + SD/Flux | ~6–7 GB | | 桌面 + 宿主程序 | ~2 GB | 前三个里任意两个加桌面就会溢出。Windows 不会当场报错，而是开始把显存换页到内存——这不会崩，只会慢 100 倍。在写下它的那台机器上实测：s2mel 扩散从 0.12 s/步 变成 30 s/步，一张图跑了 543 秒，预填从 ~1300 tok/s 掉到 0.2 tok/s。进程一直是活的。 这套东西最初就是给一个本地 AI 陪伴机器人写的：她要有人设连续性（本地 LLM）、要能发语音（IndexTTS）、要能自拍和改图（ComfyUI），而且这些经常发生在同一个回合里。通用 GPU 调度器不知道一段语音什么时候真正合成完；对陪伴场景，那个边界恰恰是最重要的。 解法不是换更大的卡，而是确保关键时刻只有一个在占显存。 它做什么. - 任务前停掉不需要的、拉起需要的，结束后再放回去。 - 真的等就绪：ComfyUI 必须 8188 在 listen，而不是进程刚起（早 1 秒连接曾让每次自拍都失败）；一批图会先等 /queue 跑空再停服务。 - 只动你列出的东西：进程名 + 命令行过滤 + 可选端口白名单，没有“杀掉所有 python.exe”这条路。 - 跨进程串行：AstrBot 插件和 DSH 插件共用 coordinator.lock，语音事件和生图任务不会同时切服务。 - 一套核心，两个宿主：AstrBot（Python 插件）与 DeepSeek Harness（原生 Cordis 插件 + 小 Python daemon）。另带 MCP stdio 服务，可给 Claude Desktop / Codex 用。 - 可复现的实测记录：docs/demo.md 有语音和生图两条交接时序，以及换页前后的数字。 适合谁. 显存协调已经不缺项目：llama-swap 6.1k★，berth 2026-10-11 才公开、已 200★，vhotseat、OneGPU4All 也在做类似的事。这个项目不假装是通用调度器，它只解决一个具体问题： > 你在 AstrBot 或 DSH 上跑一个本地 AI 陪伴：人设对话（本地 LLM）+ IndexTTS 语音 + 自拍/改图（ComfyUI），全在同一张 12 GB 卡上。 一次回合里可能同时发生： | 你的情况 | 更合适的选择 | | 只是 llama.cpp / vLLM 换模型，所有客户端都能改 base URL | llama-swap | | 要通用 GPU 租约、优先级、游戏/VM/多卡仲裁 | berth（alpha，Windows 实验性） | | Linux 上 LLM ↔ ComfyUI 轮流 | vhotseat | | 在 AstrBot / DSH 上跑本地 AI 陪伴，不想改端口、不加代理，语音合成结束才切 | 本项目 | 相对通用调度器，它多做这些： - AstrBot 的 5 个事件钩子：LLM 请求、回复装饰前后、工具调用前、工具返回后 - DSH 原生 Cordis 工具：vram_status / vram_acquire / vram_release - IndexTTS 的 tts_busy.flag / tts_ready.flag 协议（合成边界，不是 HTTP 边界） - 真实进程停启：TTS 没有 unload API 也能

Key idea

vram-switcher là công cụ điều phối GPU theo biên độ sự kiện (event boundaries), giúp luân phiên tài nguyên VRAM trên card 12 GB cho các hệ thống AI companion cục bộ (LLM, TTS IndexTTS, và ComfyUI). Công cụ giải quyết triệt để hiện tượng tràn VRAM dẫn đến Windows paging làm chậm hệ thống hàng trăm lần mà không cần proxy hay can thiệp vào mã nguồn model.

Problem

Trên GPU 12 GB, việc duy trì đồng thời LLM (~4.9 GB cho llama-server Qwen3.6-35B-A3B MoE), IndexTTS webui (~2.3–5.3 GB), ComfyUI (~6–7 GB) cùng giao diện Windows (~2 GB) gây tràn bộ nhớ. Windows không crash mà tự động swap VRAM sang RAM hệ thống khiến hiệu năng suy giảm nghiêm trọng (bước khuếch tán s2mel của TTS bị chậm từ 0.12 s/bước lên 30 s/bước, prefill LLM tụt từ ~1300 tok/s xuống 0.2 tok/s, sinh ảnh mất 543 giây). Các bộ điều phối GPU chung không nhận biết được ranh giới thực sự kết thúc của quá trình tổng hợp TTS.

Methodology

Công cụ sử dụng máy trạng thái điều khiển quá trình dừng/khởi động tiến trình theo cấu hình JSON profile (profile.local.json):

  • Giao thức Flag cho TTS: Dùng tts_busy.flag và tts_ready.flag. Khi có yêu cầu thoại, TTS plugin ghi busy flag; vram-switcher dừng LLM (và các aux_services), đảm bảo IndexTTS webui online rồi mới ghi ready flag để TTS tiến hành gọi /gen_single.
  • Đồng bộ hàng đợi sinh ảnh: Với ComfyUI, hệ thống dừng LLM/TTS, đợi cổng 8188 listen thực sự và chỉ tắt dịch vụ sau khi thăm dò /queue cạn hoàn toàn.
  • Kiểm soát tiến trình an toàn: Lọc theo tên tiến trình (process_names) kết hợp chuỗi tham số dòng lệnh (cmdline_contains/cmdline_any) và kiểm tra port; không dùng kill bừa bãi và loại trừ PID hiện tại/PID cha.
  • Khóa đa tiến trình & Đa nền tảng: Dùng tệp khóa coordinator.lock để đồng bộ giữa AstrBot (Python plugin) và DeepSeek Harness (Cordis plugin kèm daemon Python), kèm hỗ trợ giao tiếp qua MCP stdio server.

Setup

Hệ thống hỗ trợ Windows (ưu tiên NVIDIA CUDA; AMD Vulkan/DirectML/ROCm ở mức thử nghiệm). Cung cấp script tự động cấu hình python configure.py --root D:/AI để quét port và tiến trình. Hoạt động tích hợp với AstrBot, DeepSeek Harness (DSH manifest v0.15), hoặc dùng độc lập qua thư viện Python VramService.

Results

  • Khôi phục tốc độ khuếch tán s2mel của IndexTTS: từ 30 s/bước (khi bị Windows paging do tràn VRAM) trở lại 0.12 s/bước (25 bước trước đó tốn 731 giây).
  • Khôi phục tốc độ prefill LLM: từ 0.2 tok/s (khi bị tráo bộ nhớ) trở lại ~1300 tok/s.
  • Xử lý thời gian sinh ảnh ComfyUI: giải quyết tình trạng treo ảnh mất 543 giây khi bị tranh chấp VRAM.
  • Thông số hoạt động kiểm chứng: IndexTTS cold start khoảng 60 giây (timeout chờ ready đặt 150 giây); cờ tts_busy duy trì chu kỳ refresh 1.5 giây trong kịch bản gọi thoại và tự dọn dẹp cờ treo sau 900 giây (flag_stale_seconds).

Limitations

Ưu tiên chính cho Windows và card NVIDIA; hỗ trợ Linux/AMD còn hạn chế và IndexTTS trên AMD Windows rất dễ lỗi/treo do thiếu PyTorch ROCm hoàn chỉnh. Không đọc trực tiếp metric từ nvidia-smi mà suy đoán trạng thái qua tiến trình, cổng mạng và flag file. Yêu cầu TTS plugin ngoài phải tuân thủ đúng giao thức busy/ready flag.

Takeaways

Giải pháp thực dụng và hiệu quả cao cho kỹ sư triển khai pipeline đa mô hình (LLM + TTS + GenImage) trên thiết bị biên hoặc desktop GPU dung lượng thấp (12 GB) mà không cần cụm GPU rời.
